# Native ApX shaders

The Windows CoD4 renderer uses Direct3D 9 HLSL. GLSL examples need porting to that
pipeline. The community's [custom CoD4 shader introduction](https://xoxor4d.github.io/tutorials/hlsl-intro/)
documents the material → techset → technique → compiled vertex/pixel stages.
Shader-name hashing, registry pairs and the compiled-file length prefix follow
the format described by the [original shader-tool author](https://archive.raid-gaming.net/topic/1679-adding-new-sm3-hlsl-shaders-to-cod4/).

The initial effect is deliberately small: `apx_xp_fill` adds a metallic ridge to
the thin XP fill. Vertex color and alpha are preserved, and the rest of gameplay
is unaffected. It has no animated sweep, flashing, postprocessing or map shader
replacement. Its Shader Model 2 techset uses the stock flat 2D technique.

`apx_health_fill` adds a similarly quiet face to the health bar. CoD4's menu
compiler supports expression alpha, not expression RGB. The menu encodes health
in vertex alpha 0.5..1, and this pixel stage decodes it into red, gold and mint
while keeping output opacity constant. Its SM2 fallback is flat mint with at
least 50% opacity. Damage flashes are brief local HUD overlays, separate from
the shader; the shader has no clock and changes only with health.

| `src/shaders/ps_3_0_apx_health_fill.hlsl` | Health-dependent palette and static face |

| `assets/images/apx_xp_fill.iwi` | White base texture, generated by the interface tool |
| `tools/build/Shaders.cs` | Windows D3DCompiler HLSL invocation and binary/registry format |
| `tools/build/Shaders.ps1` | Per-stage cache and generated asset publication |
| `assets/shader_bin/` | Generated shader bytecode and merged name registry |

Normal All/Fastfile builds compile changed HLSL stages using Windows'
`d3dcompiler_47.dll`, without downloaded executables or external compiler installs.
Source, compiler helper/DLL, SDK registry and output hashes are checked. Editing
only the pixel source recompiles only that stage. Corrupted outputs are repaired;
`-Force` rebuilds both stages. A failed compilation preserves good bytecode and
release outputs. SDK registry changes trigger a fresh merge.

The generated registry overlays the SDK only during the existing locked linker
transaction and is restored afterward. It is not permanently installed into the
game's raw tree. Materials, techniques and bytecode link into `mod.ff`; the white
texture ships in `apx_dr.iwd`. The normal build cache still skips unchanged FFs,
IWDs and configs.

```powershell
.\tools\build.ps1
.\tools\test-shaders.ps1
```

The isolated native compiler suite covers first/no-op builds, pixel-only edits,
failed-source preservation, corrupted-bytecode repair, force rebuilds and SDK
registry preservation. SDK linking and server startup verify packaging; they do
not prove final GPU appearance in a connected client.

`apx_turntable_tall` and `apx_turntable_wide` animate 32 real mesh renders in
customization inspection pages. Their vertex stage reads engine `gameTime`; the
pixel stage samples a single atlas cell to avoid ghosted silhouettes. The vertex
stage advances the frame at eight views per second; the period is four seconds.
Animation is local to the preview rectangle and sends
no per-frame server commands. SM2 clients use still images. See [MENUS.md](MENUS.md)
for atlas generation and packaging.

`apx_preview_tall` / `apx_preview_wide` share eight full-resolution stills per
material. Separate SM2 and SM3 stages decode the vertex red channel as the cell
index, then restore a neutral red tint and preserve alpha. Native menus lack RGB
expressions, so eight mutually exclusive quads use constant cell codes; only one
is visible. This avoids using alpha as control data or interfering with fades.
The packing tests compare every source cell pixel, verify native 8-bit color
quantization, and enforce the active texture budget. The native shader tests also
compile the SM2 stages and check their bytecode version.
